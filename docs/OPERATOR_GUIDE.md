# Homebrain operator guide

Run [Smart_Swarm.command](../Smart_Swarm.command) in a terminal on Homebrain and leave it open to validate recordings. Enter **s** for the card and saved count, and **o** to open the existing [SO101 Studio recording screen](http://127.0.0.1:8020/). Select **Smart Swarm / SO101 pilot attended pilot**, native ID **`<local Studio dataset ID>`**. Use **wrist and top** in that order. The recording screen opens with no dataset selected when the recorder is idle.

## Attended preflight

Run `./smart-swarm status` for current simulation progress, saved evaluation counts and recorded physical attempts. It reads local receipts and checks the active primary worker. Run `./smart-swarm story-recording readiness` for live device and mobile-clock checks.

1. Connect the existing leader, follower, wrist camera and top camera. Check the four devices in Studio. In **Record**, select both cameras, connect their previews and distinguish the wrist motion from the fixed overhead view.
2. Clear the motion area. Run **Preflight** (`Проверить перед записью`). Retain the saved calibration. During an attended native control check, hold the leader steady and confirm that Studio accepts the saved onboard readback and shows the expected measured joints and gripper. Neither this launcher nor the dataset importer starts motion.
3. Use **STOP hands** (`STOP рук`) to end the native follow check before recording. Verify that native following has stopped. Resolve any mismatched device, calibration, camera or control readback in Studio before starting.
4. Tape the cube start, open bin footprint and neutral arm pose within the verified reach. Before motion, check from both selected cameras that the cube and bin are visible in the pickup and release areas.

## Four recording cards

In Studio use **Start recording** (`Начать запись`). Once Studio reports the episode is recording, use the native leader to grasp the cube, carry it clear of the surface, then lower, release and withdraw. Use **Save episode** (`Сохранить эпизод`) before leaving a completed attempt. Wait for motion and recording to stop before resetting with hands in the workspace.

| Attempt | Setup and observation |
| --- | --- |
| 1 | Use the taped start and open bin. Establish the nominal reachable placement and verify the terminal relation from a safe view. |
| 2 | Restore the taped cube and bin poses plus the neutral arm pose. Repeat and check whether the cube lifted with the gripper. |
| 3 | Restore the same setup. Repeat and check whether release left the cube in the bin. Save a complete failure and preserve its observed label. |
| 4 | Restore the same setup. Repeat, withdraw to neutral and leave the final scene until the outcome has been checked. |

After saving each episode and while its result is still visible, use **l** in Smart Swarm. The launcher finds the next completed attempt and asks for **s** for a stationary cube wholly in the bin and clear of the gripper, **f** for failure, or **Enter** if unclear. Keep an interrupted attempt with its native reason and count it as one of the four. Finish the recording session with the native **Stop recording** (`Остановить`) control after saving the active episode. Use native **STOP hands** if native following remains active.

Smart Swarm automatically validates and imports after the native session releases its devices. Enter **i** for a manual retry or **s** for counts. Inspect the intake reasons for failed or incomplete captures. Outcomes depend on the operator's observation. A valid complete failure is candidate story data. The four attempts stay in the development split.

## Three-agent observation

Use `./smart-swarm demo --mode mujoco --family F1` for the shared-world path. For a live session, bring up Tank's onboard computer on Homebrain's network with drive motion stopped so `<configured Tank hostname>` becomes visible. Bring up ROSMASTER on the same network with motion stopped and verify its onboard address is `<configured robot address>`. If either device is already powered, check its network association and address on its own console. Run `./smart-swarm story-recording readiness` to see current Studio STOP status, camera preview ages and both mobile robots' RGB and clock checks. Explorer's general sensor diagnostics are available through `./smart-swarm native-team`. Use the native console to verify framing, controls and STOP before attended motion.

After the distributed capture workflow passes the native-stream preflight, use **w** in the launcher to read the first story block. It contains one card for each of F1–F6. The four SO101-only cards above remain a component pilot. Story cards identify when control remains with the operator and when a human relocation must be attributed explicitly.

For the distributed setup, place one bright green square card at the station on ROSMASTER's actual left and one bright blue square at its right. Use pure colors distinct from the cyan and violet carrier marks. Keep the two station cards fixed and visible to both mobile cameras, with clear horizontal separation. Keep them outside the carriers and their movement path. The software compares Tank's view at the start and end of relocation with ROSMASTER's settled view. It uses that check to interpret the direction of Tank's association report. If the check is inconclusive, the recordings remain available and the forecast relies on the other evidence.

The native distributed recording dataset is **Smart Swarm / Distributed visual stories v1** (`<local Studio dataset ID>`), with wrist and top. Use **w** to preview the block and **r** to run its next card from the same launcher. Each card starts one read-only Explorer capture with a 60-second limit. In Studio, explicitly start and save the matching arm episode. Report the placement boundary before saving, then leave Tank at least twelve seconds around the start, relocation and settled destination. Leave time for ROSMASTER to observe the settled exterior. The launcher checks the Explorer readback and validates the single matching raw Studio episode in place. It saves ROSMASTER's decision before prompting for an evaluator reveal. Keep Studio's native top preview available for the evaluator clip. A model or human witness label remains unknown if the recorded outcome cannot be established.

After the native recording closes, Homebrain runs both frozen learned policies on their role-granted histories under the shared CPU reservation. The launcher displays the event-only search or inspection choice, the reveal-supervised comparison and the RGB rule comparison. It saves all available choices before the evaluator prompt. Keep the scene fixed during this calculation. A busy reservation or failed inference is saved as an unavailable learned forecast, with the original rule decision and recordings retained. The learned witness receives the original Tank clip with the two reference-card regions replaced by neutral RGB. ROSMASTER uses the detected station order to convert the resulting report into its own side names. Save the same setup across paired F6 trials. For a saved physical forecast, use `./smart-swarm story-recording predict --card <story-id>`. The recording keeps the reference decision, frame hashes and modeled metadata bytes. For Tank and ROSMASTER, validation uses the Explorer clock-status rows around each saved RGB receipt. A frame's full estimated capture interval and arrival must fit the declared phase. The launcher preserves an attempt as incomplete when too few frames meet that rule. The story status includes per-robot candidate counts and exclusion reasons. After a Homebrain reboot, the launcher preserves any saved prediction from the earlier clock and closes the attempt as incomplete when the reveal is still pending.

Enter a final location only after confirming that the queried object relation stayed unchanged until reveal. Keep it fixed until the launcher confirms that it saved three overhead images. Use a blank outcome if the relation stayed fixed and the location is unclear. Enter **x** if the scene changed or you cannot verify that it stayed fixed. That preserves the saved prediction and native recording as an incomplete story. A separately verified successful placement prefix remains eligible for motor review.

The launcher refreshes the physical evidence corpus after each story. Run `./smart-swarm story-recording evidence-dataset` to see admitted histories, independent source groups, terminal and event label coverage, and the reason for each rejected or incomplete attempt. A completely recorded placement failure can enter the memory corpus. The corpus preserves who acted in each phase and leaves unobserved event labels unknown. Its policy reader exposes only the scoped observations and messages available at the decision. The 24 current cards are development data.

Run `./smart-swarm story-recording evidence-score` to compare the saved RGB rule, event-only model and reveal-supervised model on the same recorded histories. The report lists unknown outcomes and unavailable predictions separately. It scores paired forecasts with verified outcomes, weighting each source block equally. The command uses the decisions already saved by the launcher.

After a story is saved, use **a** in the launcher to review an unclear outcome if it can be resolved from the recorded images. The launcher lists eligible stories and opens the automatically selected images for each reviewable phase together in capture order. Enter the number for a visible outcome and briefly describe what the images show. Press Enter to leave an outcome unknown. The launcher attaches the selected image IDs, saves the label receipt and refreshes the development corpus. This review can happen after the recording session.

For Tank's relocation assignment, confirm the left station only if the images establish which station is left from ROSMASTER's view. The F4 color identity and F6 withheld arm outcome stay masked. The terminal review uses only the evaluator overhead images. Earlier reviews use only their own witnessed phases. Conflicting reviews remain in the record and disputed labels become unknown. The original observation and the pre-reveal prediction remain available.

Run `./smart-swarm story-recording annotate --card <story-id>` to open the same review for a particular story. `annotation-proposals` displays the research audit record, including the original frame IDs and any uncalibrated RGB suggestions.

For **F3**, record the first insertion and the later removal in one Studio episode. After the first release and withdrawal, record the observed insertion outcome in the launcher before moving the cube again. The launcher retains both events for the witnessed story. A successful observed insertion can contribute a motor segment ending at that first boundary. An unknown or failed insertion stays in the story and is excluded from motor review.

F3 keeps four role-granted arm observations before the insertion marker and four after it. Use `first_insertion` for a visible first placement and `settled_placement` for the state after removal. Each label cites its own phase images.

For a placement outcome, use **s** or **f** when only native arm motion was used. Use **hs** or **hf** if hands assisted. At removal or relocation, the prompt names the change to check. Enter **h** or **r** to confirm that change by hand or by robot. Add **d** if the observed change differed or **u** if the relation stayed unclear. Enter **n** if nothing moved or press Enter if both the movement and its source are unknown. The launcher keeps the observation and assistance by phase. It only lists a motor prefix when it can map a witnessed native-arm success to the unchanged official export with both calibration readbacks. Neither hand-assisted successes nor unknown outcomes contribute motor examples. Run `./smart-swarm story-recording status` to see prepared and attempted cards, reviewable prefixes and exclusion reasons.

The corpus reports the assigned card, the observed condition and any deviation as separate fields. Save a complete recording if the planned change fails. The actual history remains useful, and the report keeps its assigned card and observed outcome. The F6 pilot cards verify withholding for a single attempt. At the end of the six-card block or when exiting with **q**, eligible placement prefixes share one official Studio export and consumer pass per native source. The scene can be reset after the reveal is saved. The motor review needs no operator action and uses the existing Studio CPU and recorder reservation. If the reservation or exporter is unavailable, the launcher keeps the prefix pending and shows the reason. `./smart-swarm story-recording review-motor` retries pending reviews and refreshes the index. `./smart-swarm story-recording motor-dataset` shows prefix totals, source groups, frame counts and exclusion reasons. Every published index identifies one immutable list of native export ranges. The reader keeps the wrist/top order and stops action chunks at the witnessed placement boundary. All first-block entries remain development data.

If the native Explorer capture ends or fails before a phase is marked, the launcher stops prompting for additional movement. It records the attempt as incomplete and keeps its terminal outcome unknown. A separately timestamped, successful Studio placement can still contribute its native prefix, including an F3 insertion completed before an interrupted removal. The launcher queues that prefix for the next motor review. Leave any active Studio controls and recording under the native operator controls, then reopen the same card after saving and stopping.

On reopen, the launcher picks the acknowledged active card ahead of an empty card. An already saved prediction or reveal is recovered from its recorded bytes. Keep the native camera-only top preview active until the three evaluator images have been saved. Smart Swarm spaces the reads and checks fresh preview status, stable device identity and native STOP generation. Each image gets a conservative post-decision timing interval based on Studio's maximum preview age. Exact exposure times remain unknown.

For read-only model replay, `./smart-swarm evidence-predict --run <sealed-episode-directory> --checkpoint <trained-checkpoint>` retains the established broadcast forecast. Choose an explicit `--query-policy broadcast`, `--query-policy latest_witness` or `--query-policy expected_information_gain` to replay the budgeted protocol and record the serialized traffic. The information-gain option uses validation priorities sealed in the checkpoint. `--through-ns` limits receipt time. The budgeted command opens image clips only for solicited witnesses.
